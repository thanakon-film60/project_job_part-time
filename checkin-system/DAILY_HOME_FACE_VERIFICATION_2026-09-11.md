# ข้อกำหนดการสแกนใบหน้าเมื่อไม่ได้ไปทำงาน

วันที่: 11 กันยายน 2026  
ระบบ: `checkin-system` — เว็บไซต์และแอปลงเวลาพนักงาน  
สถานะเอกสาร: ข้อกำหนดการใช้งานและการพัฒนาต่อ ไม่ใช่หลักฐานว่าระบบบังคับครบทุกข้อแล้ว

## 1. จุดประสงค์

ทุกวันที่ไม่ได้ไปทำงาน ผู้ใช้ต้องยืนยันตัวตนด้วยการสแกนใบหน้าและรายงานสถานะให้หัวหน้าทราบ เพื่อแสดงความรับผิดชอบต่อการรายงานตนเองในวันนั้น

**การเข้าสู่ระบบด้วยรหัสผ่านอย่างเดียวไม่ถือว่าได้ยืนยันสถานะประจำวัน และการยืนยันว่าอยู่บ้านไม่ถือว่าได้ไปทำงานหรือทำงานสำเร็จแล้ว**

## 2. กฎที่ต้องใช้

1. ทุกวันที่ไม่ได้ไปทำงาน ให้เปิดระบบและยืนยันสถานะ “อยู่บ้าน — ไม่ได้ไปทำงาน” ในวันนั้น โดยอ้างอิงวันตามเวลาไทย `Asia/Bangkok`
2. ต้องสแกนใบหน้าใหม่ **ทุกครั้งที่กดยืนยันหรือบันทึกสถานะนี้** ไม่ใช้ผลจากการลงทะเบียนใบหน้า การ login การยืนยันครั้งก่อน หรือวันก่อนแทน
3. ไม่ต้องสแกนซ้ำเพียงเพราะเปิดหน้าประวัติ เปลี่ยนหน้า หรือเปิดแชท คำว่า “ทุกครั้ง” หมายถึงทุกครั้งที่ยืนยันสถานะใหม่
4. ใช้กล้องถ่ายใบหน้าปัจจุบันและตรวจการมีชีวิตจริง (liveness) ตามขั้นตอนยืนยันตัวตน ห้ามเลือกภาพเก่ามาใช้แทนการสแกนครั้งนี้
5. ต้องผ่านการตรวจตำแหน่งบ้านที่ระบบกำหนดด้วย GPS จึงจะบันทึกสถานะที่บ้านได้
6. ถ้าสแกนไม่ผ่านหรือบันทึกไม่สำเร็จ ห้ามแสดงว่าได้ยืนยันตัวตนแล้ว
7. หากยืนยันสถานะซ้ำในวันเดียวกัน ต้องเริ่มการสแกนใหม่ ผลที่สำเร็จก่อนหน้ายังคงเป็นประวัติ ไม่ใช่สิทธิ์ข้ามการสแกนรอบใหม่
8. การส่งคำขอเดิมซ้ำเพราะเครือข่ายขัดข้องถือเป็นการส่งรายการเดิม ไม่ควรสร้างประวัติซ้ำหรือบังคับให้เริ่มรายการใหม่ก่อนตรวจว่ารายการเดิมบันทึกแล้วหรือยัง
9. ข้อกำหนดการสแกนนี้ใช้กับบัญชีที่ใช้ขั้นตอนยืนยันว่าไม่ได้ไปทำงาน รวมถึงบัญชีหัวหน้าหากใช้ขั้นตอนนี้

เอกสารนี้ยังไม่กำหนดเวลาตายตัวที่ต้องยืนยัน ไม่เพิ่มข้อยกเว้นวันหยุด/วันลา และไม่ใช้การไม่พบรายการเพียงอย่างเดียวตัดสินว่าบุคคลนั้นละทิ้งหน้าที่

## 3. ขั้นตอนสำหรับผู้ใช้

1. เปิดแอปหรือหน้าจอที่รองรับการลงเวลา แล้วเข้าสู่ระบบด้วยบัญชีของตนเอง
2. เปิดสิทธิ์กล้องและตำแหน่ง หากยังไม่มีใบหน้าอ้างอิง ให้ลงทะเบียนใบหน้าตามขั้นตอนระบบก่อน
3. เมื่ออยู่ในพื้นที่บ้าน กด “ยืนยันว่าอยู่บ้าน / ไม่ได้ไปทำงาน”
4. สแกนใบหน้าปัจจุบันและทำตามคำแนะนำบนหน้าจอจนการตรวจผ่าน
5. ระบบตรวจ GPS และบันทึกวันที่ เวลา ผู้ใช้ สถานที่ และผลการยืนยัน
6. รอข้อความยืนยันว่าบันทึกสำเร็จ แล้วตรวจว่ารายการปรากฏในประวัติของวันนี้
7. หัวหน้าตรวจสถานะผ่านเว็บไซต์ได้ หากต้องอธิบายเพิ่มเติมให้ใช้ช่องแชทส่วนตัว การส่งแชทไม่ใช้แทนการสแกนใบหน้า

หากไม่ได้อยู่บ้าน ให้รายงานสถานที่จริงกับหัวหน้า ไม่เลือกสถานะบ้านทั้งที่อยู่นอกพื้นที่ ระบบปัจจุบันยังไม่ได้กำหนดขั้นตอนยืนยันการไม่ไปทำงานจากสถานที่อื่น

## 4. สถานะและข้อความที่ควรแสดง

| เหตุการณ์ | สถานะที่แสดง | การดำเนินการ |
| --- | --- | --- |
| วันนี้ยังไม่มีการยืนยันสำเร็จ | ยังไม่ได้ยืนยันตัวตนประจำวัน | แจ้งให้สแกนใบหน้าและรายงานสถานะ |
| ยังไม่มีใบหน้าอ้างอิง | ยังไม่ได้ลงทะเบียนใบหน้า | ให้ลงทะเบียนก่อน แล้วสแกนใหม่เพื่อยืนยันสถานะ |
| กำลังสแกนหรือกำลังส่งข้อมูล | กำลังยืนยันตัวตน | รอผล ห้ามแสดงว่าสำเร็จล่วงหน้า |
| สแกนผ่าน อยู่ในเขตบ้าน และบันทึกสำเร็จ | ยืนยันตัวตนแล้ว — อยู่บ้าน / ไม่ได้ไปทำงาน | แสดงเวลาที่บันทึกและประวัติ |
| สแกนไม่ผ่าน | ยืนยันตัวตนไม่สำเร็จ | ให้ลองสแกนใหม่ |
| อยู่นอกเขตบ้าน | ไม่สามารถยืนยันสถานะที่บ้านได้ | ให้ตรวจตำแหน่งหรือแจ้งหัวหน้า |
| โหลดข้อมูลหรือบันทึกล้มเหลว | ยังตรวจสอบผลการยืนยันไม่ได้ | ตรวจประวัติ/ลองเชื่อมต่อใหม่ ไม่สรุปว่าผู้ใช้ไม่รับผิดชอบ |

ตัวอย่างข้อความเตือน:

> วันนี้ยังไม่ได้ยืนยันตัวตน หากไม่ได้ไปทำงาน กรุณาสแกนใบหน้าและยืนยันสถานะที่บ้าน เพื่อรายงานตัวและแสดงความรับผิดชอบต่อหน้าที่

ตัวอย่างข้อความหลังบันทึกสำเร็จ:

> ยืนยันตัวตนและรายงานสถานะแล้ว: อยู่บ้าน — ไม่ได้ไปทำงาน บันทึกเวลา {เวลาไทย}

## 5. ผลต่อการลงเวลาและรายงาน

**ข้อยืนยันจากผู้ใช้: อยู่บ้านไม่ต้องมีเวลาเข้างานหรือสถานะสายใด ๆ ทั้งสิ้น**

- ไม่มีเวลาเข้างาน ไม่มีเวลาออกงาน และไม่ต้องกดออกงานเมื่ออยู่บ้าน
- ไม่ใช้เกณฑ์ 08:30–17:30 หรือช่วงผ่อนผันกับการยืนยันสถานะที่บ้าน
- ไม่แสดงป้ายสาย ตรงเวลา มาก่อนเวลา ออกก่อนเวลา ครบเวลางาน หรือทำงานเกินเวลาในรายการและการ์ดสถานะบ้าน
- ไม่แสดงเวลาเข้า–ออกที่คาดหวังหรือช่องเข้า–ออกว่างในสรุปสถานะบ้าน และไม่นับชั่วโมงทำงานจากรายการบ้าน
- ใช้ข้อความ “ยืนยันตัวตนแล้ว — อยู่บ้าน / ไม่ได้ไปทำงาน” หลังสแกนและบันทึกสำเร็จ
- หากเก็บวัน–เวลาที่สแกนไว้ในประวัติ ให้เรียกว่า “เวลายืนยันตัวตน” เท่านั้น ไม่เรียกว่าเวลาเข้างาน และไม่นำไปตัดสินว่าสาย

- สถานที่: “ถึงบ้านแล้ว” ใช้ `category=home` รัศมี 200 เมตร และ `allow_checkout=false` ตามค่าที่คืนกลับเมื่อ 11 กันยายน 2026
- รายการที่บ้านเป็นหลักฐานการรายงานตัว ไม่ใช่รายการไปทำงาน
- ไม่เพิ่มจำนวนวันมาทำงาน ไม่รวมเป็นชั่วโมงทำงาน และไม่ตัดสินสายหรือออกก่อนเวลา
- ไม่ต้องมีรายการออกงานจากบ้านคู่กัน
- เมื่อมีรายการที่บ้านสำเร็จ ให้แสดงว่ายืนยันตัวตนแล้วในวันนั้น พร้อมระบุชัดว่าไม่ได้ไปทำงาน
- ถ้าวันเดียวกันภายหลังไปสำนักงาน ให้แสดงประวัติบ้านและการไปสำนักงานตามเวลาจริง โดยคำนวณงานจากรายการสถานที่ทำงาน
- ข้อความแจ้งเตือนหัวหน้าต้องระบุว่าอยู่บ้าน/ไม่ได้ไปทำงาน ไม่ใช้ข้อความที่ทำให้เข้าใจว่าเข้างานที่สำนักงาน

## 6. สิ่งที่ตรวจพบในระบบปัจจุบัน

| ส่วน | พฤติกรรมปัจจุบัน | สิ่งที่ต้องพัฒนาหากจะบังคับตามเอกสารนี้ครบ |
| --- | --- | --- |
| พิกัดบ้าน | คืนเข้ารายการสถานที่ของ production แล้ว | คงประเภท `home` และข้อกำหนดไม่ให้ออกจากงานที่บ้าน |
| API ลงเวลา | พนักงานต้องส่ง `face_detected=true`; บัญชีหัวหน้าถูกยกเว้น | การยืนยันว่าไม่ได้ไปทำงานต้องไม่ข้ามการสแกนเพียงเพราะเป็นหัวหน้า |
| หลักฐานการสแกนฝั่ง server | Endpoint รับ `face_detected` จาก client และรับรูปภาพแบบไม่บังคับ | ค่า boolean นี้อย่างเดียวไม่พิสูจน์ว่าเพิ่งสแกน ต้องตรวจหลักฐานการสแกนสดที่ผูกกับผู้ใช้และรายการนี้ พร้อมป้องกันนำผลเดิมมาใช้ซ้ำ |
| ปุ่มลงเวลาที่บ้านใน source แอปพนักงาน | ปิดปุ่มหลังมีรายการบ้านของวันนี้ | หากให้ผู้ใช้ยืนยันซ้ำ ต้องเปิดขั้นตอนใหม่และสแกนใหม่ทุกรอบ |
| หน้าเว็บ | มีหน้าประวัติใบหน้าและแสดงสถานะลงเวลา การลงเวลาปัจจุบันชี้ไปแอปมือถือ | การลงทะเบียนใบหน้าบนเว็บไม่ใช่การยืนยันสถานะรายวัน หากต้องลงเวลาจากเว็บ ต้องเพิ่มขั้นตอนนี้โดยตรง |
| สรุปการยืนยันรายวันบนเว็บ | ตรวจการมีใบหน้าอ้างอิงและรายการลงเวลาในวันนั้น | ต้องแยกการมีรายการลงเวลากับการมีหลักฐานสแกนสด เมื่อบังคับใช้กฎใหม่ |
| APK ที่แจก | รอบงานก่อนหน้ายังเป็น binary เก่า | ต้องตรวจและ build/publish แอปที่รองรับกฎใหม่ก่อนอ้างว่าผู้ใช้ทุกเครื่องใช้งานได้แล้ว |

**การสร้างไฟล์นี้ไม่ได้เปลี่ยนโค้ด ไม่ได้ยกเลิกข้อยกเว้นหัวหน้า และไม่ได้เพิ่มหน้าสแกนบนเว็บไซต์โดยอัตโนมัติ**

**สถานะบ้านไม่มีเวลาเข้า–ออก ไม่มีสาย/ตรงเวลา ไม่มีชั่วโมงทำงาน และไม่ใช้ตาราง 08:30–17:30 แม้ผู้ใช้จะยืนยันช่วงเย็นหรือกลางคืน** วันตามประเทศไทยใช้จัดกลุ่มประวัติเท่านั้น ไม่ใช่เส้นตายในการยืนยัน

### 9.1 จุดที่ต้องแก้ใน source

เส้นทาง `lib/...` ในตารางหมายถึงใต้โฟลเดอร์แอปทั้งสอง เว้นแต่ระบุว่าเฉพาะแอปพนักงาน

| ไฟล์ | งานที่ต้องทำ |

แอปหัวหน้ายังไม่มีชุด `face_scanner.dart` / `face_service.dart` / `face_enroll_screen.dart` แบบแอปพนักงาน และเส้นทางส่ง check-in เดิมมี `faceDetected: false` ต้องเพิ่มขั้นตอนกล้องและตรวจ dependencies/permissions ของ Android และ iOS ให้ครบ ห้ามยกเว้นด้วยบทบาทหัวหน้าใน flow บ้าน

ไฟล์ใหม่ที่เสนอให้สร้างเมื่อเริ่มเขียนโค้ด: `lib/models/home_verification.dart`, `lib/services/home_verification_service.dart`, `lib/screens/home_verification_screen.dart` และ `lib/widgets/home_verification_card.dart` ในทั้งสองแอป หรือใช้ shared package ตามโครงสร้างที่ทีมตกลง ไฟล์เหล่านี้ยังไม่ใช่ไฟล์ที่มีอยู่แล้ว

## 10. หน้าจอและลำดับการทำงานของแอป

1. เปิดหน้าแรก: โหลดสถานะวันนี้จาก server โดยแยกสถานะกำลังโหลด/โหลดไม่ได้ออกจาก “วันนี้ยังไม่ได้ยืนยัน” การ login หรือเปิดแชทไม่เปลี่ยนสถานะรายวัน
2. กด “ยืนยันว่าอยู่บ้าน / ไม่ได้ไปทำงาน”: ตรวจ session สิทธิ์กล้องและตำแหน่ง โหลดพื้นที่บ้าน และตรวจว่ามีใบหน้าอ้างอิง หากยังไม่มี ให้ลงทะเบียนก่อนแล้วกลับมาสแกนสำหรับรายการนี้
3. ขอ challenge ใหม่จาก server แล้วเปิดกล้องเพื่อเก็บหลักฐานสดตามรูปแบบที่ backend รองรับ ไม่เลือกภาพจากแกลเลอรีหรือใช้ภาพลงทะเบียนแทน
4. รับพิกัดปัจจุบัน ตรวจความพร้อมและพื้นที่บ้าน ถ้าอยู่นอกบ้าน ให้แจ้งตามจริง ไม่เลือกบ้านให้เองและไม่บันทึกว่ารายงานสำเร็จ
5. ส่งหลักฐานและพิกัดด้วย request ID ของรอบนี้ ปิดการกดซ้ำระหว่างส่ง แสดงสำเร็จต่อเมื่อ server ยืนยันว่าบันทึกแล้ว
6. แสดง “ยืนยันตัวตนแล้ว — อยู่บ้าน / ไม่ได้ไปทำงาน” พร้อมชื่อสถานที่ รีเฟรชประวัติและข้อมูลที่หัวหน้าเห็น หากแสดง timestamp ในประวัติ ใช้ชื่อ “เวลายืนยันตัวตน” เท่านั้น
7. เปิดปุ่ม “ยืนยันสถานะอีกครั้ง” เพื่อเริ่มรอบใหม่และสแกนใหม่ การดูผลเดิม เปลี่ยนหน้า หรือเปิดแชทไม่สร้างรายการเพิ่ม

สถานะที่แนะนำสำหรับ controller (ชื่อเพื่อออกแบบ ไม่ใช่ class ที่มีแล้ว):

```text
loading → unverified / verified / loadFailed
unverified หรือ verified → preparing → scanning → submitting → verified
preparing หรือ scanning → blocked / cancelled
submitting → rejected / resultUnknown
resultUnknown → ตรวจผลด้วย request ID เดิม → verified / rejected / รอตรวจต่อ
```

- `blocked`: กล้อง/GPS ถูกปฏิเสธ อยู่นอกพื้นที่ หรือยังไม่พร้อม ให้ทางกลับไปตั้งค่าและลองใหม่
- `rejected`: server ปฏิเสธอย่างแน่นอน เช่น หลักฐานไม่ผ่าน ต้องเริ่มสแกนใหม่ตาม error code
- `resultUnknown`: timeout หรือเน็ตหลุดหลังส่ง อาจบันทึกไปแล้ว ให้แสดง “ยังตรวจสอบผลการยืนยันไม่ได้” และตรวจรายการเดิมก่อนเริ่มคำขอใหม่
- เมื่อแอปพักระหว่างสแกน ให้หยุดกล้องและยกเลิกหลักฐานที่ยังไม่ส่ง กลับมาแล้วเริ่มรอบใหม่ หากส่งไปแล้วแต่ยังไม่ทราบผล ให้รักษา request ID เพื่อกู้ผลเดิม
- เมื่อออกจากหน้าให้ dispose กล้องและ subscription ตรวจ `mounted`/ยกเลิก callback ที่หมดอายุ ไม่ให้ผลจากหน้าหรือบัญชีเก่ามาเปลี่ยนหน้าปัจจุบัน

## 11. API ปัจจุบันและสัญญาที่ต้องพัฒนาเพิ่ม

### 11.1 API ที่มีอยู่แล้ว

| API | การใช้งานปัจจุบันและข้อจำกัด |
| --- | --- |
| `GET /reports/geofence` | โหลดพื้นที่และตารางงาน ใช้รายการประเภท `home` สำหรับบ้าน โดยบ้านไม่ใช้ตารางงาน |
| `GET /checkins/me?days=1&limit=200` | โหลดรายการของผู้ใช้ ตรวจการแบ่งวันไทยให้ถูกต้อง ข้อมูลลงเวลาเก่าไม่ใช่หลักฐานว่าผ่านการตรวจสแกนสดแบบใหม่ |
| `POST /checkins` | multipart: `latitude`, `longitude`, `kind`, `face_detected` และ `photo` ที่ปัจจุบันไม่บังคับ; `kind` รองรับ `in`/`out` เท่านั้น |

ระบบเดิมใช้ `kind=in` สำหรับรายการบ้าน แล้ว server เลือกสถานที่จากพิกัด **อย่าส่ง `kind=home` ให้ endpoint เดิมโดยไม่ได้แก้ backend** การตั้ง `face_detected=true` หรือส่งรูปอย่างเดียวไม่ใช่หลักฐานยืนยันตัวตนสดที่เชื่อถือได้ และ backend เดิมยังยกเว้นการตรวจ boolean ให้หัวหน้า

สถานที่บ้านที่คืนไว้: “ถึงบ้านแล้ว”, latitude `13.8865664`, longitude `100.5066278`, radius `0.2` กิโลเมตร, `category=home`, `allow_checkout=false` ค่านี้เป็นข้อมูลอ้างอิงของการตั้งค่ารอบนี้ แอปต้องโหลดค่าล่าสุดจาก server ไม่ฝังเป็นแหล่งข้อมูลหลัก

### 11.2 สัญญาใหม่ที่เสนอ — ยังต้องทำ backend ก่อนใช้งาน

ชื่อ endpoint และ field ต่อไปนี้เป็นข้อเสนอสำหรับตกลงร่วมกับ backend ไม่ใช่ API ที่เรียกได้ใน production ขณะจัดทำเอกสาร

| Endpoint ที่เสนอ | ข้อมูลสำคัญ |
| --- | --- |
| `POST /home-verifications/challenges` | ใช้ session ปัจจุบัน รับ `challenge_id`, `expires_at`, `server_time` และคำสั่ง/รูปแบบหลักฐานที่ต้องเก็บ โดย challenge ผูกกับบัญชีและการยืนยันบ้าน |
| `POST /home-verifications` | ส่ง `request_id`, `challenge_id`, `latitude`, `longitude`, `location_accuracy_m` และหลักฐานสดตาม verifier ที่ backend เลือก; ห้ามใช้คะแนนหรือ boolean จาก client เป็นคำตัดสิน |
| `GET /home-verifications/requests/{request_id}` | ตรวจผลคำขอเดิมเฉพาะเจ้าของบัญชี รองรับกรณีส่งสำเร็จแต่ response หาย |
| `GET /home-verifications/me?date=YYYY-MM-DD` | รับรายการและผลรายวันตาม `Asia/Bangkok` พร้อมวันปัจจุบันของ server เพื่อไม่เชื่อเวลาบนอุปกรณ์อย่างเดียว |

ผลสำเร็จที่เสนอให้ทั้งเว็บและ Flutter ใช้ร่วมกัน:

```json
{
  "id": "verification-id",
  "request_id": "client-generated-uuid",
  "status": "verified",
  "category": "home",
  "office_name": "ถึงบ้านแล้ว",
  "verified_at": "2026-09-11T14:15:00Z",
  "local_date": "2026-09-11",
  "timezone": "Asia/Bangkok"
}
```

ตัวอย่างเวลาเป็นเวลาบันทึกหลักฐาน ไม่ใช่เวลาเข้างาน ไม่ต้องเพิ่ม `late_minutes`, `expected_check_in`, `expected_check_out` หรือชั่วโมงทำงานในโมเดลบ้าน

ข้อกำหนดฝั่ง backend ที่ต้องทำคู่กัน:

- ตรวจ session, ความเป็นเจ้าของ challenge, อายุหลักฐาน, liveness/การตรงกับใบหน้าอ้างอิง และพื้นที่บ้านก่อนบันทึก โดยไม่มีข้อยกเว้นหัวหน้า ต้องเลือกและเชื่อม verifier ที่ตรวจได้จริง ไม่เชื่อค่าที่ Flutter ประกาศเอง
- อายุ challenge ใช้ป้องกันหลักฐานเก่า ไม่ใช่เวลาที่ผู้ใช้ต้องยืนยันก่อนจึงจะไม่สาย
- ผูก `request_id` กับบัญชีและ payload พร้อม unique constraint/transaction ส่งคำขอเดียวกันซ้ำต้องคืนรายการเดิม ไม่สร้างรายการเพิ่ม รวมกรณีคำขอพร้อมกัน
- หากคำขอนั้นบันทึกแล้ว ให้คืนผลเดิมก่อนตรวจว่า challenge หมดอายุหรือถูกใช้แล้ว หากใช้ ID เดิมแต่เปลี่ยน payload ให้ปฏิเสธ เช่น HTTP 409
- ไม่พบ request ID ยังไม่ยืนยันว่าคำขอแรกหยุดทำงานแล้ว ต้องรองรับการส่งซ้ำด้วย ID เดิมอย่างปลอดภัย และเก็บผลให้ครอบคลุมช่วงกู้คืนที่ประกาศในสัญญา API
- คำขอใหม่หลังรายการเดิมสำเร็จต้องใช้ request ID และ challenge ใหม่ พร้อมสแกนใหม่ ห้ามใช้ proof เดิมสร้างรายการใหม่
- ใช้เวลาบันทึกจาก server เป็นหลัก กรณีส่งข้ามเที่ยงคืนให้ใช้ `local_date` ของรายการที่ server บันทึกจริง ตรวจผลย้อนหลังด้วย request ID ได้แม้เปลี่ยนวัน
- ส่ง error code ที่แยก session หมดอายุ, ต้องลงทะเบียนใบหน้า, challenge หมดอายุ, หลักฐานไม่ผ่าน, นอกพื้นที่ และคำขอขัดแย้ง เพื่อให้แอปแสดงแนวทางแก้ที่ถูกต้อง
- จัดทำสิทธิ์อ่านรายงานหัวหน้าตามความสัมพันธ์เดิม และปรับรายงาน/เว็บไซต์ให้อ่านผลยืนยันใหม่ด้วย โดยไม่รวมบ้านเป็นงานและไม่อ้างว่ารายการบ้านเก่าผ่าน verifier ใหม่

## 12. การจัดเก็บข้อมูลและความเข้ากันได้

- โมเดลบ้านแยกจาก work session; `verifiedAt` เป็น UTC ที่มี timezone ชัดเจน แปลงแสดงด้วย `Asia/Bangkok` และใช้ `localDate` จาก server สำหรับรายวัน
- ข้อมูลใหม่ใช้ `category` ที่ server ส่ง ข้อมูล check-in เก่ายังต้องรองรับการจำแนกผ่าน `office_name` ตาม `LocationService.isHomeName` จนมีการย้ายข้อมูล ห้ามเดาว่าทุก `kind=in` เป็นเข้างาน
- วันที่มีทั้งบ้านและสำนักงาน ให้แสดงสองเหตุการณ์แยกกัน คำนวณเวลางานจากรายการสำนักงานเท่านั้น สถานะบ้านต้องไม่ปิดหรือเปิด work session
- เมื่อผล API เก่าและใหม่ครอบคลุมเหตุการณ์เดียวกัน ให้กำหนดแหล่งข้อมูลหลักและ ID อ้างอิงชัดเจน เพื่อไม่แสดงซ้ำหรือรวมยอดซ้ำ
- เก็บเฉพาะข้อมูลกู้คำขอที่จำเป็นแยกตามบัญชี ไม่บันทึก token/ภาพใบหน้า/หลักฐานลง log ล้างไฟล์กล้องชั่วคราวหลังใช้งาน และล้างข้อมูลส่วนตัวเมื่อ logout
- ไม่ตั้งเวลาตายตัวสำหรับเตือนว่าสาย และไม่สร้างรายการสำเร็จอัตโนมัติเมื่อ offline ข้อความเตือนรายวันต้องเป็นกลาง เช่น “วันนี้ยังไม่ได้ยืนยันสถานะ”
- หาก backend ยังไม่รองรับสัญญาใหม่ ให้แจ้งว่าฟังก์ชันยังไม่พร้อม ห้าม fallback ไป `face_detected=true` แล้วแสดงว่าผ่านการยืนยันสดแบบใหม่

## 13. ลำดับส่งมอบงานสำหรับทีม Flutter และ backend

1. อ่านเอกสารนี้และ `HANDOVER_OFFICE_MOVE_2026-09-10.md` พร้อมตรวจ `AGENTS.md` ก่อนแก้โค้ด ตรวจ source ปัจจุบันอีกครั้งเพราะเลขบรรทัดและสัญญา API อาจเปลี่ยน
2. ทำ backend contract, verifier, การป้องกันคำขอซ้ำ และชุดทดสอบก่อนเปิดใช้ UI ใหม่ ตกลงรูปแบบ evidence และ error response กับทีม Flutter
3. เพิ่มโมเดล/service/controller บ้านโดยยึดรูปแบบ state management ที่โปรเจกต์ใช้อยู่ ไม่ต้องย้าย state management ทั้งแอป
4. ทำหน้าบ้านและ scanner ในแอปพนักงาน แล้วทำความสามารถเดียวกันในแอปหัวหน้า รวมการขอสิทธิ์กล้อง/GPS และกรณียังไม่ลงทะเบียนใบหน้า
5. แก้ข้อความบ้านในปุ่ม หน้า scanner หน้าผลสำเร็จ การ์ดวันนี้ ประวัติ รายงาน และข้อความแจ้งเตือนให้ตรงกัน แชทใช้คุยเพิ่มเติมได้ แต่ไม่แทนการสแกน
6. เชื่อมการ refresh หลังบันทึกกับประวัติ เว็บ และหน้ารายงานหัวหน้า ตรวจวันไทยและวันผสมบ้าน/สำนักงาน
7. ตรวจบน staging ด้วยบัญชีทดสอบพนักงานและหัวหน้า แล้วจึง build แอปทั้งสองตามขั้นตอน release ของโปรเจกต์

## 14. เกณฑ์ทดสอบก่อนส่งต่อ APK

| กรณี | ผลที่ต้องได้ |
| --- | --- |
| อยู่บ้านยืนยันเช้า บ่าย หรือกลางคืน | ได้ผลบ้านเหมือนกัน ไม่มีสาย/ตรงเวลา/เวลาเข้า–ออก/ชั่วโมงทำงาน |
| การ์ดบ้านและประวัติ | ใช้ข้อความยืนยันสถานะ ไม่มีช่องเข้า–ออกว่าง ไม่มีตารางงาน; timestamp ถ้ามีเรียก “เวลายืนยันตัวตน” |
| login อย่างเดียว หรือมีภาพลงทะเบียนแล้ว | ไม่กลายเป็นยืนยันรายวันสำเร็จ |
| พนักงานและหัวหน้ายืนยันบ้าน | ต้องสแกนสดเหมือนกันทั้งสองบทบาท |
| ยืนยันใหม่ในวันเดิม | เปิดปุ่มได้ ต้องสแกนและขอ challenge ใหม่ |
| เปิดหน้าซ้ำหรือเปิดแชท | ไม่บังคับสแกนเพื่อดูผลและไม่เพิ่มรายการ |
| รูปเก่า proof เดิม หรือ challenge ของบัญชีอื่น | server ปฏิเสธ ไม่บันทึกรายการใหม่ |
| GPS ปิด สิทธิ์ถูกปฏิเสธ หรืออยู่นอกบ้าน | บอกสาเหตุและให้ลองใหม่ ไม่รายงานสำเร็จ |
| เน็ตหลุดหลังส่ง กดซ้ำ หรือปิดเปิดแอป | ตรวจผลด้วย request ID เดิม เหลือรายการเดียว ไม่อ้างว่าล้มเหลวแน่นอนเมื่อยังไม่ทราบผล |
| เปลี่ยนวันไทย/ตั้งเวลาเครื่องผิด/ส่งข้ามเที่ยงคืน | อิงวันและเวลาจาก server ไม่ใช้รายการเมื่อวานแทนวันนี้ และไม่สร้างสถานะสาย |
| อยู่บ้านแล้วไปสำนักงานวันเดียวกัน | แสดงทั้งสองเหตุการณ์ เวลางานนับจากสำนักงานเท่านั้น |
| logout แล้วสลับบัญชี | ไม่เห็นผล หลักฐาน หรือคำขอค้างของบัญชีก่อนหน้า |
| backend ยังไม่พร้อมหรือ session หมดอายุ | แสดงข้อผิดพลาดที่แก้ไขได้ ไม่ข้ามการยืนยันด้วยวิธีเดิม |

ให้เพิ่ม unit test สำหรับโมเดล/วันไทย/การแยกบ้านออกจากงาน, widget test สำหรับข้อความและปุ่ม, integration test สำหรับกล้อง/GPS/เน็ตหลุด และ backend test สำหรับหลักฐานกับ idempotency ตามความเสี่ยงจริง ทดสอบสิทธิ์และวงจรกล้องบนอุปกรณ์จริงด้วย

คำสั่งตรวจเมื่อเครื่องพัฒนามี Flutter SDK พร้อมแล้ว ให้รันในแต่ละโฟลเดอร์ `flutter_app` และ `flutter_boss_app`:

```powershell
flutter pub get
flutter analyze
flutter test
flutter build apk --release
```

คำสั่ง build ต้องใช้ signing และ environment ของโปรเจกต์จริง ตรวจ integration test ด้วยคำสั่งตามชุดทดสอบที่เพิ่มขึ้น หากส่ง iOS ต้องใช้เครื่อง macOS และกระบวนการ signing ของ iOS เพิ่มเติม

- [ ] บันทึกผลตรวจทั้งสองแอปและ backend พร้อมข้อจำกัดที่ยังเหลือ
- [ ] ตรวจ app version/build number, API environment และ compatibility ก่อน build
- [ ] ตรวจ APK ที่จะเผยแพร่ตรงกับ source ที่ผ่านการทดสอบจริง ไม่ใช้ APK เก่าแทน
- [ ] ตรวจทุกช่องทางดาวน์โหลดหลังเผยแพร่และ smoke test บนอุปกรณ์จริง
- [ ] อัปเดตเอกสารนี้ว่าข้อใดทำแล้ว รุ่นใด และข้อใดยังไม่เสร็จ โดยไม่ใช้การแก้เอกสารเป็นหลักฐานว่า deploy แล้ว

## 15. ข้อความสำหรับส่งต่องานพัฒนา

> พัฒนาการยืนยันว่าอยู่บ้าน/ไม่ได้ไปทำงานตามเอกสารนี้ใน Flutter ทั้ง `flutter_app` และ `flutter_boss_app` พร้อม backend ที่ตรวจหลักฐานสดจริง ทุกการยืนยันใหม่ต้องสแกนใหม่รวมบัญชีหัวหน้า บ้านไม่มีเวลาเข้า–ออก ไม่มีสาย/ตรงเวลา และไม่คิดชั่วโมงทำงาน ต้องกู้ผลคำขอเมื่อเน็ตหลุดโดยไม่สร้างรายการซ้ำ ปรับหน้าแรก หน้าสแกน หน้าสำเร็จ ประวัติ และรายงานให้ตรงกัน อ่านข้อจำกัด API เดิมก่อนเริ่ม ห้ามถือว่า `face_detected=true` คือหลักฐานสด ทดสอบทั้งสองแอปแล้วบันทึกรุ่นและผลทดสอบก่อนส่ง APK
