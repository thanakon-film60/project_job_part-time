## 3. ✅ สิ่งที่ Production ต้องอัปเดต

### 3.1 ตั้งค่าใน `.env` ของ backend

เพิ่ม/แก้บรรทัดเหล่านี้ (ดูตัวอย่างสำหรับ backend ใน `checkin-system/backend/.env.example`; ไฟล์ที่ process production อ่านจริงคือ `checkin-system/backend/.env`):

```env
# --- สถานที่ทำงาน (JSON บรรทัดเดียว) ---
OFFICES=[{"name":"Motta & Montipa (Head office)","lat":13.9040518,"lng":100.5391995,"radius_km":0.5,"category":"work"}]

# --- เวลาทำงาน (เวลาไทย) ใช้ตัดสิน สาย / ออกก่อน ---
WORK_START_TIME=08:30
WORK_END_TIME=17:30
LATE_GRACE_MINUTES=0
EARLY_LEAVE_GRACE_MINUTES=0
ATTENDANCE_RULES_ENABLED=true
```

| ตัวแปร | ความหมาย | ค่าที่ตั้งไว้ |
| --- | --- | --- |
| `WORK_START_TIME` | เวลาเข้างานมาตรฐาน | `08:30` |
| `WORK_END_TIME` | เวลาออกงานมาตรฐาน | `17:30` |
| `LATE_GRACE_MINUTES` | ผ่อนผันกี่นาทีถึงเริ่มนับว่าสาย | `0` = เข้า 08:31 สายทันที |
| `EARLY_LEAVE_GRACE_MINUTES` | ออกก่อนเกินกี่นาทีถึงเตือน | `0` |
| `ATTENDANCE_RULES_ENABLED` | สวิตช์ปิดฟีเจอร์ทั้งระบบ | `true` |

> ⚠️ ไฟล์ `.env` ต้องเป็น **UTF-8 ไม่มี BOM** (ชื่อสถานที่มีอักขระ `&`)
> และ `OFFICES` ต้องอยู่ **บรรทัดเดียว** ห้ามตัดบรรทัด

**ถ้าอยากให้ผ่อนผัน 15 นาที** (เข้าถึง 08:45 ยังไม่ถือว่าสาย)
ตั้ง `LATE_GRACE_MINUTES=15` — ตัวเลขนาทีที่รายงานยังนับจาก 08:30 เหมือนเดิม
เพราะนั่นคือเลขที่ HR ใช้

## 4. ตรรกะการตัดสิน "สาย / ตรงเวลา"

### 4.1 ตอนเข้างาน (`kind = "in"`)

| เวลาที่กด | ผล | ข้อความ |
| --- | --- | --- |
| 08:15 | ตรงเวลา | `ตรงเวลา (ก่อนเวลา 15 นาที)` |
| 08:30 | ตรงเวลา | `ตรงเวลา` |
| 08:31 | **สาย** | `สาย 1 นาที` |
| 10:05 | **สาย** | `สาย 1 ชม. 35 นาที` |

- เส้นตัดสิน = `WORK_START_TIME + LATE_GRACE_MINUTES`
- **จำนวนนาทีที่รายงานนับจาก 08:30 เสมอ** ไม่ใช่นับจากเส้นผ่อนผัน
  (ผ่อนผัน 15 นาที แล้วเข้า 08:46 → รายงาน "สาย 16 นาที")

### 4.2 ตอนออกงาน (`kind = "out"`)

| เวลาที่กด | ผล | ข้อความ |
| --- | --- | --- |
| 16:30 | **ออกก่อนเวลา** | `ออกก่อนเวลา 1 ชม.` |
| 17:30 | ครบเวลา | `ครบเวลางาน` |
| 18:45 | ครบเวลา | `ครบเวลางาน (เกินเวลา 1 ชม. 15 นาที)` |

### 4.3 กรณีที่ "ไม่ตัดสิน"

- ลงเวลาที่ **บ้าน** (category `home`) — อยู่บ้าน = ไม่ได้ไปทำงาน
  ตรรกะเดิมของระบบอยู่แล้ว ไม่มีสาย/ไม่มีออกก่อน
  *(ตอนนี้ไม่มีพิกัดบ้านในระบบแล้ว แต่โค้ดยังรองรับถ้าเพิ่มกลับมา)*
- ตั้ง `ATTENDANCE_RULES_ENABLED=false`
- `kind` ไม่ใช่ `in`/`out`

### 4.4 ข้อจำกัดที่รู้อยู่ (ตั้งใจ)

- **เทียบเฉพาะ "เวลาในวัน" ไม่ดูวันที่** — ระบบนี้เป็นกะกลางวัน
  ลงเวลาตอนตี 1 จะนับว่า "มาก่อนเวลา" ไม่ใช่สายข้ามวัน
  ถ้าอนาคตมีกะดึกต้องออกแบบใหม่
- **ไม่ได้เก็บสถานะสายลง DB** — คำนวณสดจากเวลาที่บันทึกไว้ทุกครั้ง
  ข้อดีคือแก้เกณฑ์ย้อนหลังแล้วรายงานเก่าถูกต้องตาม เกณฑ์ใหม่ทันที
  ถ้า HR ต้องการล็อกสถานะ ณ วันนั้น ต้องเพิ่มคอลัมน์ใน `checkins` (งานคนละก้อน)
- **ไม่รู้จักวันหยุด/วันลา** — เสาร์อาทิตย์กดเข้างาน 10 โมงก็ขึ้นว่าสาย
  ยังไม่มีตารางวันหยุดในระบบ

## 9. สถานะงานต่อเนื่องหลังอัปเดตเว็บไซต์

- **หน้าเว็บ (frontend)** ทำแล้วและ deploy แล้ว: ป้ายสาย/ตรงเวลา/ออกก่อน/ครบเวลา ในหน้าพนักงาน รายละเอียดปฏิทินหัวหน้า และประวัติรายบุคคล พร้อมแสดงสำนักงานและเกณฑ์ที่โหลดจาก backend
- **สรุปรายเดือนบนเว็บ** ทำแล้วในหน้าประวัติรายบุคคล: จำนวนวันมาสายจากเข้างานครั้งแรก และจำนวนวันออกก่อนจากออกงานครั้งสุดท้ายของแต่ละวัน (ไม่นับรายการบ้านและไม่นับซ้ำจากการกดหลายครั้ง); ยังไม่ได้เพิ่มรายงาน export หรือเปลี่ยน API รายงาน
- **ตารางวันหยุด/วันลา** ยังไม่มี (ดูข้อจำกัดหัวข้อ 4.4)
- **ที่อยู่แบบตัวอักษร** ของออฟฟิศใหม่ ยังว่างอยู่ (ดูหัวข้อ 2)

### 10.5 APK ที่ยังต้องทำก่อนปิดงานทั้งหมด

ตรวจ `/app/info` และ `/boss-app/info` บน production แล้ว:

| แอป | เวอร์ชันที่แจกจริง | วันที่ build ตาม metadata | เวอร์ชันใน source |
| --- | --- | --- | --- |
| พนักงาน | `1.2.0+3` | 25 สิงหาคม 2026 | `1.5.0+7` |
| หัวหน้า | `1.0.0+1` | 30 สิงหาคม 2026 | `1.2.0+4` |

APK สำรองใน `flutter_app/thanakon-checkin.apk`, `flutter_boss_app/app-release.apk` และ `flutter_boss_app/build/app/outputs/flutter-apk/app-release.apk` เป็น binary เก่าเช่นเดียวกับไฟล์ที่แจก ไม่มีค่าฟีเจอร์ `work_schedule`/`late_grace_minutes` หรือชื่อสำนักงานใหม่ใน library ที่ตรวจ จึงยังไม่ได้ publish ทับหรือเปลี่ยน metadata ให้ดูเหมือนเป็นเวอร์ชันใหม่

ไม่พบ Flutter/Android SDK บนเซิร์ฟเวอร์นี้ และ path ใน `flutter_boss_app/android/local.properties` ชี้เครื่องพัฒนาเดิม (`C:\src\flutter`, SDK ใต้ user `Pac-Man45`) ซึ่งไม่มีบนเครื่องนี้

ขั้นตอนที่เครื่องพัฒนาที่มี SDK:

1. ใช้ source ปัจจุบันของทั้ง `flutter_app` และ `flutter_boss_app`; รัน `flutter analyze` และ `flutter test` ในแต่ละแอปก่อน build
2. Build APK release โดยรักษา applicationId และ signing key เดิมของแต่ละแอป เพื่อให้อัปเดตทับของเดิมได้ (ลายเซ็นของ APK พนักงานและหัวหน้าที่แจกอยู่เป็นคนละใบ)
3. ส่ง APK ใหม่สองไฟล์มายังเซิร์ฟเวอร์ แล้วใช้คำสั่งด้านล่างหลังตรวจเวอร์ชันภายใน APK และลายเซ็นแล้ว:

```powershell
# รันจาก checkin-system; เปลี่ยน path ให้เป็นไฟล์ใหม่ที่ build จริง
.\deploy\windows-server\publish-apk.ps1 -ApkPath '<employee-release.apk>' -Version '1.5.0+7' -MinSdk 24
.\deploy\windows-server\publish-apk.ps1 -Boss -ApkPath '<boss-release.apk>' -Version '1.2.0+4' -MinSdk 24
```

4. ตรวจ `/app/info`, `/boss-app/info`, ดาวน์โหลดและติดตั้งทับเครื่องที่ใช้งานจริง แล้วตรวจป้ายสาย/ตรงเวลาของแอปทั้งสอง

แอปเก่ารับพิกัดใหม่ผ่าน API ตามกลไกเดิมได้ แต่การแสดงป้ายสถานะบนแอปต้องใช้ APK ใหม่; การทำงานจริงของ APK เก่ายังไม่ได้ทดสอบกับเครื่อง Android ในรอบนี้
