# รายงานปัญหา: ปุ่ม "ฟังเสียงจากกล้อง" ไม่ขึ้นในแอปหัวหน้า

**ผู้แจ้ง:** ทีมเซิร์ฟเวอร์ · **วันที่ตรวจ:** 2 ก.ย. 2026
**ขอบเขต:** ฝั่งแอป Flutter (`flutter_boss_app`) — ฝั่งเซิร์ฟเวอร์ตรวจแล้วปกติดี
**ความรุนแรง:** ปานกลาง (ฟีเจอร์ใช้ไม่ได้จนกว่าผู้ใช้จะรู้วิธี refresh เอง)

---

## สรุปสั้น

แอปเก็บค่า `audioSupported` ไว้ตั้งแต่ตอนเปิดแท็บกล้องครั้งแรก **แล้วไม่โหลดใหม่อีกเลย**
ถ้าเซิร์ฟเวอร์เพิ่งเปิดความสามารถนี้ทีหลัง แอปจะยังขึ้นข้อความว่าใช้ไม่ได้ค้างอยู่
ตลอดไป ทั้งที่เซิร์ฟเวอร์พร้อมแล้ว — สลับแท็บหรือรอเฉย ๆ ก็ไม่หาย

**ต้องแก้:** ให้แอปโหลด `/camera/status` ใหม่เมื่อผู้ใช้กลับเข้ามาดูแท็บกล้อง
หรือเมื่อแอปกลับมา foreground

**ไม่ต้องแก้:** ฝั่ง backend, การติดตั้งเซิร์ฟเวอร์, ตัวกล้อง — ตรวจครบแล้วทั้งหมด

---

## อาการที่ผู้ใช้เจอ

เปิดแอปหัวหน้า → แท็บ "กล้องวงจรปิด" → ตรงที่ควรมีปุ่มฟังเสียง ขึ้นข้อความสีจาง:

> เซิร์ฟเวอร์นี้ยังส่งเสียงจากกล้องไม่ได้

ภาพสดกับการหมุนกล้อง (PTZ) ใช้งานได้ปกติ มีแต่ส่วนเสียงที่ไม่มีปุ่มให้กด
**ปุ่มไม่ปรากฏเลย** ไม่ใช่กดแล้วไม่ทำงาน

---

## สิ่งที่ตรวจแล้วว่า "ไม่ใช่" สาเหตุ

ฝั่งเซิร์ฟเวอร์ตรวจครบเมื่อ 2 ก.ย. 2026 ผลออกมาว่าพร้อมใช้งานทุกอย่าง

### 1. เงื่อนไขที่ backend ใช้ตอบ `audio_supported`

`GET /camera/status` คำนวณจาก 2 อย่างที่ [`camera.py:206-208`](../backend/app/routers/camera.py#L206-L208)
รันด้วย venv ของโปรเจกต์บนเครื่อง production ได้ผล:

```
camera_audio_enabled : True
find_ffmpeg()        : C:\ProgramData\chocolatey\bin\ffmpeg.exe
audio_supported      : True      <-- เซิร์ฟเวอร์ตอบ true แล้ว
```

> เดิม ffmpeg ไม่ได้ถูกติดตั้ง (ขั้นที่ 1 ของ `CAMERA_SETUP.md` เขียนว่าข้ามได้
> ถ้าไม่ใช้เสียง จึงถูกข้ามไป) ติดตั้งแล้วเมื่อ 2 ก.ย. 2026 เวลา 10:07 น.
> ด้วย `choco install ffmpeg -y` ได้ ffmpeg v9.0.1
> **ไม่ต้อง restart backend** เพราะ `find_ffmpeg()` ถูกเรียกใหม่ทุกครั้งที่มีคำขอ

### 2. กล้องส่งเสียงมาจริงไหม

ทดสอบดึงเสียงจาก `rtsp://192.168.1.101:554` ตรง ๆ ด้วยโค้ดตัวเดียวกับที่ API ใช้
(`camera_audio.AudioStream`) กล้องตอบ:

```
Stream #0:0: Video: hevc (Main), 2304x1296
Stream #0:1: Audio: pcm_alaw, 8000 Hz, mono, 64 kb/s
```

รันซ้ำ **4 รอบติดกัน ผ่านทั้งหมด** ได้ข้อมูลเสียง AAC รอบละ 16 KB
ใช้เวลาเริ่มส่งราว **9.4 วินาที** ทุกรอบ (สอดคล้องกับที่เอกสารระบุว่ากล้องใช้เวลาราว 6 วิ)

### 3. IIS ส่งต่อ `/camera/*` ไป backend หรือยัง

เคยเป็นปัญหาจริงและ **แก้ไปแล้ว** เมื่อ 2 ก.ย. 2026 — `web.config` บนเครื่อง production
ไม่มี `camera` ในกฎ `ProxyToBackend` ทำให้ `/camera/status` ได้ HTML กลับไปแทน JSON
รายละเอียดอยู่ใน [`FIX_CAMERA_ROUTING.md`](../deploy/windows-server/FIX_CAMERA_ROUTING.md)
ตอนนี้ `/camera/status` ตอบ `application/json` และตรวจครบทุก router แล้ว

## สาเหตุที่แท้จริง (ฝั่งแอป)

### จุดที่แสดงข้อความ

[`camera_tab.dart:807-817`](lib/screens/tabs/camera_tab.dart#L807-L817) — ถ้า
`audioSupported` เป็น false จะ `return` ออกตั้งแต่ต้น ไม่สร้างปุ่มเลย:

```dart
Widget _buildAudioRow() {
  final status = _status;
  if (status == null || !status.audioSupported) {
    return const Padding(
      ...
      child: Text('เซิร์ฟเวอร์นี้ยังส่งเสียงจากกล้องไม่ได้', ...),
    );
  }
  ...
```

### ทำไมค่าถึงค้าง

`_loadStatus()` ถูกเรียกจาก `initState()` ที่ [บรรทัด 109](lib/screens/tabs/camera_tab.dart#L109)
คือ **ครั้งเดียวตอนสร้าง widget** หลังจากนั้นมีอีกแค่ 2 ทางที่จะโหลดใหม่:

| ทาง | ใช้ได้กับเคสนี้ไหม |
| --- | --- |
| ผู้ใช้ pull-to-refresh ([บรรทัด 477](lib/screens/tabs/camera_tab.dart#L477)) | ได้ แต่ผู้ใช้ไม่มีทางรู้ว่าต้องทำ |
| timer ลองใหม่อัตโนมัติทุก 20 วิ ([บรรทัด 215-224](lib/screens/tabs/camera_tab.dart#L215-L224)) | **ไม่ทำงานในเคสนี้** |

timer ตัวนั้นมีเงื่อนไข:

```dart
final needsRetry = _visible && _foreground && !_loadingStatus &&
    (_statusError != null || !(_status?.canControl ?? false));
```

และ `canControl` คือ [`enabled && reachable`](lib/models/camera.dart#L50) — **ไม่เกี่ยวกับเสียงเลย**

ในเคสนี้กล้องต่อติดปกติ (`enabled=true`, `reachable=true`) และไม่มี error
→ `needsRetry` เป็น false → timer ถูกยกเลิก → **แอปไม่โหลดสถานะใหม่อีกเลย**

### สลับแท็บก็ไม่ช่วย

`app_shell` ใช้ [`IndexedStack`](lib/screens/app_shell.dart#L179) ซึ่งเก็บ state ของแท็บที่ซ่อนไว้
widget ไม่ถูก dispose → `initState()` ไม่ถูกเรียกใหม่ → ค่าเดิมยังอยู่

**สรุป: ค่าที่ผิดจะค้างจนกว่าผู้ใช้จะ pull-to-refresh หรือปิดแอปแล้วเปิดใหม่**

## ข้อเสนอวิธีแก้

### แนวทางที่แนะนำ — โหลดสถานะใหม่เมื่อผู้ใช้กลับมาดูแท็บ

ครอบคลุมปัญหาทุกแบบที่เกิดจาก "ความสามารถฝั่งเซิร์ฟเวอร์เปลี่ยนหลังแอปเปิดค้าง"
ไม่ใช่แค่เรื่องเสียง และไม่เพิ่มภาระเพราะยิงเฉพาะตอนผู้ใช้กลับเข้ามาจริง ๆ

- ใน `didChangeDependencies()` ตอนที่ `_visible` เปลี่ยนจาก false เป็น true
  ให้เรียก `_loadStatus(silent: true)`
- ใน `didChangeAppLifecycleState()` ตอนกลับเป็น `resumed` ให้เรียกเช่นกัน

### ทางเลือกเสริม — ทำให้ข้อความกดได้

ตอนนี้ข้อความเป็น `Text` เฉย ๆ ผู้ใช้เจอทางตัน ไม่รู้ว่าต้องทำอะไรต่อ
เพิ่มปุ่ม "ลองเช็คใหม่" ข้าง ๆ ที่เรียก `_loadStatus()` จะช่วยได้มาก
และควรบอกให้ชัดว่าเป็นข้อจำกัดของเซิร์ฟเวอร์ ไม่ใช่ของแอป

> **หมายเหตุ:** ไม่ต้อง build APK ใหม่เพื่อแก้ปัญหาเฉพาะหน้า —
> ค่านี้มาจาก API ตอน runtime ผู้ใช้ pull-to-refresh ก็เห็นปุ่มแล้ว
> การแก้โค้ดคือกันไม่ให้เกิดซ้ำในอนาคต

## เรื่องที่ "ไม่ใช่" งานของทีมแอป (แจ้งเพื่อทราบ)

### 1. กดพูดออกลำโพงกล้อง (talkback) — ติดที่เฟิร์มแวร์กล้อง

`talkback_supported` ถูกกำหนดเป็น `false` ตายตัวที่ [`camera.py:212-229`](../backend/app/routers/camera.py#L212-L229)
ทีมเซิร์ฟเวอร์ตรวจกับกล้องจริง (ONVIF cloudCam fw 43.4.0.0) แล้วพบว่ากล้อง *มี* ลำโพง
(`GetCapabilities` ตอบ `AudioOutputs = 1`) แต่เฟิร์มแวร์ไม่เปิดช่องส่งเสียงเข้า:

- `RTSP OPTIONS` ไม่มี `ANNOUNCE` / `RECORD`
- `DESCRIBE` พร้อม header backchannel ตอบ SDP เดิม ไม่มี track `a=sendonly`

ต้องแก้ที่ตัวกล้อง (setting หรืออัปเฟิร์มแวร์) **ฝั่งแอปทำอะไรไม่ได้**
โค้ดแอปรองรับไว้แล้ว จะแสดงปุ่มเองทันทีที่เซิร์ฟเวอร์ตอบ `true`

### 2. ARR อาจ buffer สตรีมเสียง — ยังไม่ยืนยัน ทีมเซิร์ฟเวอร์รับไปดูต่อ

ตรวจ `applicationHost.config` พบว่า ARR proxy ตั้งไว้แค่

```xml
<proxy enabled="true" preserveHostHeader="false" reverseRewriteHostInResponseHeaders="false" />
```

ที่เหลือใช้ค่า default ตาม `arr_schema.xml` ซึ่งมี 2 ตัวที่กระทบสตรีมโดยตรง:

| attribute | ค่า default | ผลต่อสตรีมเสียง |
| --- | --- | --- |
| `minResponseBuffer` | 256 (KB) | ARR สะสมข้อมูลให้ถึงเกณฑ์ก่อนค่อยส่งต่อให้ client |
| `bufferChunkedResponses` | true | บัฟเฟอร์ response แบบ chunked ซึ่งเป็นวิธีที่ FastAPI ใช้ส่งสตรีม |

เสียงเข้ารหัสที่ 32 kbit/s ≈ 4 KB/s → กว่าจะสะสมครบ 256 KB ใช้เวลา **~64 วินาที**
ขณะที่แอปตั้ง `_audioConnectTimeout` ไว้ [25 วินาที](lib/screens/tabs/camera_tab.dart#L28)

**ยังไม่ได้ยืนยัน** เพราะ `/camera/audio` ต้องใช้ token ผู้จัดการ ทดสอบทะลุ IIS ไม่ได้
ทีมเซิร์ฟเวอร์มีขั้นตอนวัดผลอยู่ใน
[`SERVER_TASKS_CAMERA_AUDIO.md`](../deploy/windows-server/SERVER_TASKS_CAMERA_AUDIO.md) แล้ว

ถ้าหลังแก้เรื่อง refresh แล้วปุ่มขึ้นมา แต่กดแล้วขึ้นว่า
**"ต่อเสียงไม่ทัน — กล้องไม่ส่งเสียงมา"** ให้แจ้งทีมเซิร์ฟเวอร์
อย่าเพิ่งไปไล่แก้ที่แอปหรือขยาย timeout เพราะต้นเหตุอยู่ที่ IIS
(ภาพนิ่งกับ PTZ ไม่โดนผลกระทบ เพราะเป็น response สั้น ๆ ที่จบในตัว
มีแต่เสียงที่เป็นสตรีมไม่รู้จบ)

## สิ่งที่ทำไปแล้ว (2 ก.ย. 2026)

### ฝั่งแอป — ตรงตามที่รายงานเสนอ

`_loadStatus(silent: true)` ถูกเรียกเมื่อกลับเข้ามาดูแท็บ และเมื่อแอปกลับเป็น `resumed`
มีตัวกันไม่ให้ยิงซ้ำถี่เกินไป (สถานะที่โหลดมาไม่เกิน 15 วินาทีถือว่ายังใช้ได้)

ทำ "ทางเลือกเสริม" ที่รายงานแนะนำด้วย — ข้อความตอนใช้เสียงไม่ได้มีปุ่ม **"ลองเช็คใหม่"**
และข้อความมาจากเซิร์ฟเวอร์ (`audio_note`) แทนที่จะเป็นข้อความกลาง ๆ ที่แอปเดาเอง

เทสต์ที่เพิ่ม (`test/camera_tab_test.dart`) — ย้อนโค้ดกลับเป็นแบบเดิมแล้วยืนยันว่าเทสต์จับได้จริง:

- เซิร์ฟเวอร์เปิดเสียงทีหลัง แล้วกลับเข้าแท็บ ปุ่มต้องโผล่เอง
- สลับแท็บไปมาเร็ว ๆ ต้องไม่ยิงถามสถานะรัว ๆ
- ปุ่ม "ลองเช็คใหม่" สั่งโหลดสถานะได้
- แสดงเหตุผลที่กดพูดไม่ได้ตามที่เซิร์ฟเวอร์ถามกล้องมา

### เกินขอบเขตรายงาน: เจอรอยรั่วที่ทำให้กล้องช้าลงเรื่อย ๆ

ระหว่างทดสอบบนเครื่องจริงพบว่า **ffmpeg ไม่เคยถูกฆ่าเลย** — กดฟังเสียงไม่กี่ครั้ง
เหลือค้าง 13 ตัว ทุกตัวจับ RTSP ของกล้องไว้ ทำให้กล้องช้าลงจนภาพนิ่งกับ PTZ พลอยหลุดไปด้วย

สาเหตุ: `terminate()` ฆ่าได้แค่ shim ของ chocolatey ส่วน ffmpeg ตัวจริงที่เป็นลูกรอด
แก้แล้วสามชั้น (ฆ่าทั้งต้นไม้ / ffmpeg ตัวเดียวแจกทุกคน / เพดานอายุสตรีม)
รายละเอียดอยู่ใน [`SERVER_TASKS_CAMERA_AUDIO.md`](../deploy/windows-server/SERVER_TASKS_CAMERA_AUDIO.md)

### เรื่องปุ่มกดพูด — ข้อมูลในรายงานไม่ครบ

รายงานสรุปว่า "ติดที่เฟิร์มแวร์กล้อง ฝั่งแอปทำอะไรไม่ได้" ซึ่งถูกเฉพาะทาง ONVIF/RTSP
แต่ **แอป iCam365 ของผู้ผลิตกดพูดได้จริง** แปลว่ากล้องรองรับ เพียงแต่ไม่ได้เปิดทางนั้น
ผ่านมาตรฐานที่เราใช้ — สแกนครบ 65535 พอร์ตแล้วเจอโปรโตคอลเฉพาะของผู้ผลิตอีก 5 พอร์ต

และ `talkback_supported` ไม่ได้เขียนตายตัวเป็น `false` อีกแล้ว เซิร์ฟเวอร์ไปถามกล้องจริง
ทุกครั้ง เปลี่ยนกล้อง/อัปเฟิร์มแวร์เมื่อไร ปุ่มขึ้นเองโดยไม่ต้องแก้โค้ด
